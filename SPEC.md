# PersonaStack for Omarchy specification

## Purpose

Provide a desktop client for PersonaStack on Omarchy with the complete user-visible functionality of `macos-desktop`.

The Electron shell and Go companion implement the hosted desktop session, sign-in handoffs, pop-outs, local harness setup, Desktop Control lifecycle, and bounded local executor in source. The implementation is incomplete and no Omarchy profile or feature is certified. The full parity baseline and completion evidence live in the active workspace plan. This spec records the repository's ownership boundaries and desired outcome.

## Authority

- `personastack-api` owns identity, authorization, workspaces, personas, product state, enrollment and revocation.
- `my.personastack.ai` owns authenticated hosted pages, OAuth callbacks, browser-facing composition, notifications event data and pop-out routes.
- `mcp` and `agent-gateway` own reviewed Desktop Control tools, typed request contracts, transport and routing.
- This client owns Linux window presentation, the finite native bridge, local harness setup, protected machine credential custody, outbound connection lifecycle, and bounded GUI, filesystem and process execution.
- Hyprland and Cua own their compositor and device-control interfaces. This application must use a pinned supported driver/plugin contract and must not claim support for behavior that the tested target profile cannot provide.

The client must not create a second login, authorization service, integration store, product database, realtime event authority, MCP catalog or gateway protocol.

## Supported environment

No environment is currently supported. The first candidate is Omarchy Edge on x86_64 with an exact Omarchy, Hyprland, Electron, Cua Driver, Cua Hyprland input plugin and Secret Service profile recorded by the feasibility gate. The pinned optional input-v3 plugin is experimental and only qualifies the documented Calc and Inkscape package versions on its exact Hyprland ABI and compiler toolchain. Its documented raw background-input path excludes Chromium, Electron, and XWayland. The desktop app uses Electron through XWayland, so this plugin alone cannot provide the required background-input parity. No alternate Hyprland raw background-input adapter is implemented. Do not report the GUI-control parity row as complete until every required action has a verified route on the candidate profile. ARM64, other Linux distributions, other compositors, stable-channel Omarchy and unsupported Cua applications are outside the initial claim until separately proven.

## Authentication

The client uses the existing PersonaStack sign-in methods and hosted session authority. Google account sign-in opens the configured desktop-handoff start route in the system browser. The hosted site requires an explicit CSRF-protected approval after sign-in. The API issues a short-lived, single-use code bound to the active session, native attempt, exact app origin and PKCE challenge. The `personastack://` callback carries only the attempt ID and code. Electron redeems the code through its persistent hosted session. The hosted site sets its normal HttpOnly cookie. The client never imports system-browser cookies or receives the API bearer token in a URL or renderer. Google Services OAuth opens only the exact Google authorization endpoint whose redirect URI matches the configured app origin and callback path and whose state was issued by the API. Electron launches that URL in the system browser and reloads the hosted integration page when the user returns.

## Native window controls

The Linux shell selects XWayland because its chat bridge uses Electron's programmatic move, resize and always-on-top controls. [Electron documents](https://www.electronjs.org/docs/latest/api/base-window) these APIs as unavailable or restricted on native Wayland. [Electron recommends](https://www.electronjs.org/docs/latest/api/browser-window) `--ozone-platform=x11` when an app needs these capabilities. This backend selection is implemented, but its behavior is not certified on Omarchy. Test transparency, collapse/expand, drag, monitor clamping, minimize/restore and above-normal placement on the pinned Electron and Hyprland profile. [Hyprland documents](https://wiki.hypr.land/0.46.0/Configuring/Dispatchers/) its `pin` dispatcher as showing a floating window on every workspace. That does not implement the required current-workspace pin behavior. Do not report the chat window's pin action as working until native state readback confirms it.

On Hyprland, the Linux chat Pin action registers an app-generated initial-title token and the Electron process ID with a local adapter. It matches exactly one XWayland client in `hyprctl clients -j` by `initialTitle`, `pid`, and `xwayland`; it does not rely on an X11 window ID field that Hyprland does not emit. The adapter reads `monitors -j`, then uses the compositor address with `alterzorder top` only while the chat's workspace is active on its monitor. It listens to Hyprland's local event socket for active-window, monitor, workspace, move, open and close changes. Missing or ambiguous client matches do not dispatch. It does not invoke focus or pin the window across workspaces. If Hyprland's session variables, event socket or query path are unavailable, Electron's always-on-top request remains in effect. This implementation is source-only until its exact XWayland and Hyprland behavior passes native acceptance.

## Security boundary

Remote content receives only finite presentation messages from registered top-level windows at the configured PersonaStack app origin. Machine credentials stay in protected OS storage and native process memory. The API authorizes each workspace, persona and Desktop Control operation. Native execution accepts only reviewed typed operations under the current lease and scope. A failed or uncertain mutation is not replayed automatically.

The current Electron shell uses a persistent, origin-specific browser partition. It disables renderer Node integration, enables context isolation and sandboxing, and admits native bridge calls only from registered current main frames at the exact configured origin and document generation. The hosted `/auth/oidc/start` route from any app window uses the desktop handoff and opens in the system browser. A canceled auth navigation rolls back its provisional document generation so the current hosted page keeps its bridge. Google authorization requests are blocked in Electron in keeping with [Google OAuth policy](https://developers.google.com/identity/protocols/oauth2/policies#use_secure_browsers). Google account sign-in and enterprise SSO start through the system-browser handoff so Google authorization never runs in an app-controlled embedded user agent. Google Services OAuth opens in the system browser only when its exact Google authorization URL targets the configured app-origin callback and carries its API-issued state; Electron keeps the hosted integration route pending until the first app return or for at most ten minutes. On that first return it refreshes the route once. If the user returns before the browser callback completes, they must refresh the hosted page after completing the browser flow. Google authorization frames are blocked. All other external subframe navigation is blocked. User-clicked external HTTP(S) links open in the system browser, and mailto links open with the OS mail handler. Product-domain links with target=_blank also open externally. Ordinary same-product links stay in-app. The hosted native-operation bridge is unavailable away from the configured app origin. The isolated preload can still open a validated user-clicked HTTP(S) link from the registered main window. Browser permission requests are denied away from the configured app origin. Other external navigation remains denied. A main-window navigation away from the app closes authenticated pop-outs. Hosted same-product navigation remains in-app without retaining bridge privileges on a different origin. Concern, chat, chat-window, stack, Local Session, and Desktop Control bridge names are exposed. Hosted Desktop Control supports `sync`, `state`, and `prepare`; the reserved `desktop:lifecycle` scope is only available to the native tray path. The Linux tray reads app-wide lifecycle state and exposes pause/resume/repair/disconnect through a separate finite companion command path without changing or depending on hosted workspace scope. Only this tray state path reads current API relay activity. Hosted local installation state remains available during relay-status outages. The tray distinguishes a user's saved pause from an inactive relay, reports unavailable native runtime separately, disables Resume and setup after a failed or pending status read, and preserves Pause when a live Gateway or cached active relay allows a safe local fence. Repair fences local execution, restarts the owned Cua process, and replaces damaged driver files only when the pinned ownership marker and known file layout verify; unknown files and foreign paths are preserved. A failed repair leaves execution paused. Disconnect requires native confirmation and revokes all workspace mappings for the installation through the existing API client before deleting the keyring credential. A failed revoke leaves the installation credential available and the runtime paused for retry. The tray retains lifecycle action errors through status polling. The setup action opens `/user/desktop-control` in the main window. Local Session supports the hosted versioned `state`, `select_harness`, `prepare`, and `configure` messages through the Go companion, bounded login-shell probes and process-group cleanup, API-owned bundle validation, and a PersonaStack-owned Linux plugin installer. `internal/desktoplifecycle` owns setup-time Cua preparation, API enrollment/attachment/revocation, Gateway connection and reconnect, executor startup, startup recovery, aggregate relay cleanup, explicit pause/resume persistence, repair and disconnect fencing, and the Hyprland lock monitor. Agent Gateway owns API session preparation and claim during the authenticated WebSocket handshake. Setup waits for a fresh heartbeat acknowledgement before reporting Gateway readiness. The executor starts with unknown lock state and rejects commands until the lock monitor observes an unlocked session. `internal/hyprlandlock` queries `hyprctl -j locked` and fences the executor to unknown on read failures. `internal/desktopexecutor` contains finite Cua dispatch, bounded screenshot results, scoped lease/revocation policy, and the lock fence. `internal/desktoplocal` connects the bounded Linux file and process managers to the executor. Desktop Control `prepare` reports native runtime readiness. An unconfigured setup session can remain alive for ten minutes while the first workspace config is saved. Linux starts the pinned Cua 0.30.1 `cua-driver mcp` process as a supervised stdio child with no socket argument and negotiates MCP `2025-06-18`. The Cua child retains the current `HYPRLAND_INSTANCE_SIGNATURE` from the compositor session while continuing to exclude machine credentials. A shared command runner owns local CLI process groups, terminates descendants on timeout, and caps inherited output-pipe waits. Cua documents that this process owns its Linux runtime directly by default, so PersonaStack does not perform ambient daemon discovery or touch an externally managed daemon. The owned child explicitly selects Cua's `standard` permission mode instead of inheriting mode changes from its environment; PersonaStack API installation, workspace, persona, and lease checks remain the authorization boundary for remote commands. Only the owned child receives telemetry and update-check overrides. An MCP protocol or reported driver-version mismatch leaves Cua unready and sets the tray's typed `cua_upgrade_required` state until a successful preparation or repair. Linux window controls use Electron through XWayland. Native window/tray icons load from the packaged PNG asset and fail at startup if the image cannot be decoded. Host-specific compositor behavior remains unverified, and no native Wayland window-control adapter is implemented. Electron frame and origin checks admit bridge calls; PersonaStack API remains the authority for user and workspace authorization. Real plugin-manager runs in disposable Linux profiles verified installation, readback, and preservation of unrelated settings against Codex CLI 0.157.1 and Claude Code 2.1.152. They do not establish provider authentication, MCP connectivity, deployed Gateway authorization, native session/sign-in behavior, or Omarchy compatibility.

Pop-out windows are scoped to the authenticated hosted workspace. A change to the synchronized workspace scope closes every persona chat, stack graph/stream, and activity window together. Logout, denied or failed main-window navigation, and renderer termination also invalidate all pop-outs. Same-scope synchronization preserves existing windows.

## Parity outcome

Implement the required journeys in the active plan: hosted app/login and notifications; chat, stack and activity windows; Codex and Claude setup; installation enrollment and status; all reviewed GUI actions; bounded files and managed processes; lock, revocation, reconnect, packaging and lifecycle. Completion requires native evidence for the advertised Omarchy profile. A passing source test or tool response alone does not certify native behavior.
